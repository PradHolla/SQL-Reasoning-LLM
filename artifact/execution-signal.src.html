01 The task, and why it's hard

Given a database schema and a question in English, emit SQL that answers it.

-- input
Schema:   CREATE TABLE head (head_ID INT, name TEXT, born_state TEXT, age REAL);
          CREATE TABLE department (Department_ID INT, Name TEXT, Budget REAL);
          CREATE TABLE management (department_ID INT, head_ID INT, acting TEXT)
Question: How many heads of the departments are older than 56?

-- target
SELECT count(*) FROM head WHERE age > 56

The SQL surface here is trivial. The hard part is schema linking: deciding that "heads of the departments" means the head table and not management, and that "older than" is age and not one of thirty-nine other columns. Get the syntax right and the column wrong and you have a query that runs beautifully and returns the wrong answer.

Nearly every result below turns out to be about that one problem. The models are small on purpose — 0.5B and 1.5B parameters, LoRA adapters, one 24 GB GPU — because the interesting question is how much can be extracted from a weak model rather than how a large one performs.

The benchmark is Spider: ~10,000 human-written questions over 200 real SQLite databases, split so the test databases never appear in training. You cannot pass it by memorising one schema; you have to read one you have never seen.

02 Measurement: the executor

Everything rests on one function: run the predicted query and the reference query against the real database, and compare the rows that come back. Not string similarity, not AST equality — execution accuracy.

This matters because the obvious alternative fails immediately. Exact string matching scores age>56 as zero against age > 56: identical queries, identical results, no credit. And there are usually many correct queries for one question.

Comparison semantics

"Same rows" needs pinning down, and each choice moves the number:

DecisionChoiceWhy
Row multiplicitymultisetSet comparison makes SELECT name and SELECT DISTINCT name indistinguishable. Spider's official script uses sets, so our numbers read slightly lower than published ones.
Column orderignoredBounded permutation search. Answering age, name for name, age is presentation, not correctness.
Row orderonly when the reference says soDerived from whether the gold query has a non-window ORDER BY.
Numerics9 significant digitsSo SUM(x)/COUNT(x) and AVG(x) agree despite float noise.
Connectionread-onlyModel-authored SQL can contain DROP TABLE. If that ever landed, every later evaluation against that database would be silently wrong.
Timeoutprogress handlersqlite3.connect(timeout=) bounds lock acquisition only, and would let a runaway join spin forever.

Known limitation, measured rather than hiddenAn empty result set matches an empty reference, so WHERE 1=0 scores on any question whose true answer is empty. That cannot be fixed inside a comparison function. Instead it is quantified: 54 of 2,147 reference answers are empty (2.5%), and accuracy is reported both with and without them. If the two diverge, the headline is propped up by questions nobody actually answered.

Four numbers, because one cannot say why

Every run reports parse rate, execution rate, execution accuracy, and structural match. The gaps between them are the diagnosis. Parse 99% with execution 65% means the model is inventing columns. Execution 90% with accuracy 30% means it writes valid SQL answering a different question — a reasoning problem, not a syntax one. A single accuracy number cannot distinguish those.

Contamination

Before trusting any score, we hash-compared benchmark questions against the training corpus. 562 of Spider dev's 1,034 questions appear verbatim in the training set, reference SQL included — the common sql-create-context corpus is partly built from Spider.

Any dev score was therefore partly a memorisation score. The primary benchmark moved to Spider test (16 of 2,147 overlapping, 0.7%, disjoint databases). This affects every project trained on that corpus and evaluated on Spider dev, which is a great many of them.

Guarding the metric itself

Two failure modes in the measuring apparatus, both found the hard way:

An empty prediction returned "ok" with zero rows from SQLite, which compares equal to any empty reference — a free point for generating nothing. A query producing no result set is now an error.

And the SQL parser's cost is exponential in JOINs without an ON clause: 12 joins parse in 0.04s, 20 in 11.2s, more never return. A degenerate model output stopped an evaluation run dead. The executor had a timeout; the parser did not, and a parser that never returns cannot be interrupted. It is now bounded by limits derived from the benchmark itself — across all 3,181 reference queries the longest is 608 characters with 6 joins.

The executor sits underneath the two highlighted stages and under evaluation, which is the organising idea of the project: in reinforcement learning your evaluation and your reward are the same skill. Build one and you get the other. It later became the filter for synthetic training data, and then the grouping function for inference-time voting. One component, four jobs.

04 Supervised fine-tuning

Three decisions carry most of the weight.

Train on full schemas

The widely-used sql-create-context corpus supplies schemas pruned to exactly the columns the answer needs. A model trained on that never learns to read a schema, which is the actual task. Its failures at evaluation are 88% invented columns and tables. Rebuilding on Spider with real database schemas is the single largest change in the project.

Mask the prompt

With full schemas the prompt is roughly 75% of the tokens in a training example. Computing loss over the whole sequence means most of the gradient teaches the model to generate database schemas. Completion-only loss puts every gradient step on the answer.

Validation loss picks the wrong checkpoint

Epoch 2 looked slightly worse than epoch 1 on both validation loss and token accuracy, and was +3.9 points of real execution accuracy. Loss is a proxy for a proxy. Run the metric you actually care about, on held-out data, at every checkpoint.

ResultOriginal pipeline 6.4% → rebuilt SFT 44.6%. For scale, the untrained base model scores 17.4% with its best prompt, so the original three-stage pipeline had been performing worse than no training at all.

05 An execution-grounded RL reward

GRPO (Group Relative Policy Optimization) samples several answers to the same prompt, scores each, and pushes the policy toward the ones that scored above their group's average. The advantage for rollout i is roughly:

advantage_i = (reward_i − mean(group)) / std(group)

Read that formula carefully, because it dictates the reward design. If every rollout in a group scores identically, the numerator is zero for all of them and the group contributes no gradient at all.

The original setup had two rewards: a format reward worth +1.0 that fired for essentially every sample, and exact string match worth +2.0 that fired for almost none. So a group of four scored [1.0, 1.0, 1.0, 1.0]. The diagnostic for this, frac_reward_zero_std, sat between 0.5 and 1.0 and reached 1.00 by step 160 — a large share of 300 training steps did literally nothing.

A ladder with partial credit

OutcomeRewardSignal it provides
no SQL found, or it will not parse0.0—
parses as SQL0.2syntax is a solved sub-problem
the database accepted and ran it0.5tables and columns actually exist
result set matches the reference2.0correct

Now a group where nothing is fully correct still scores [0.2, 0.5, 0.5, 0.2] — genuine disagreement, genuine gradient. The 0.5 tier is aimed squarely at the dominant failure: it pays specifically for the columns existing.

# the mechanism, not just the score — failure counts before → after RL
unknown_column   647 → 458   (−29%)
unknown_table     66 →   7   (−89%)

Result44.6% → 49.7%, McNemar χ² = 29.7, p < 0.001. It fixed 251 questions and broke 142 — the +5.1 is a net, not a clean sweep, and reporting it as a net matters.

Three implementation details that each silently break it

Reward scaling cancels the ladder. TRL's default scale_rewards="group" divides each group's scores by that group's own standard deviation. The ordering of the tiers survives; the spacing does not. A group whose best answer was genuinely correct then pushes exactly as hard as one whose best answer merely parsed — the careful ladder degenerates into "rank within group". Set to "none", which preserves a 7.5× spread between "correct" and "parsed".

The KL reference is not what you think. Under LoRA, TRL's reference policy is the adapter switched off — the raw base model, not your SFT checkpoint. A large, constant KL is therefore measuring how far supervised fine-tuning already moved, not what RL is doing. We set beta=0 rather than regularise toward a model we had deliberately trained away from.

Result-size caps must be lossless. The reward caps rows at len(gold_rows) + 1. Any prediction returning more rows than that cannot match under multiset comparison, so the cap can never change a verdict — it just stops a hallucinated cross join from materialising a million rows inside the training loop.

Attacking the reward before spending on it

Reward hacking is normally discovered from a reward curve that climbs while the benchmark stays flat — that is, after the GPU hours are spent. Instead we wrote eleven question-blind policies and measured what each could extract:

SELECT 1                       — always parses, never matches
SELECT * FROM <first table>    — always executes
SELECT COUNT(*) FROM <table>   best: 26.8% of gold's mean reward, 1.8% exact match
WHERE 1 = 0                    — exploits the empty-result equality
degenerate cross joins         — tests the row cap and parser guards

The best lazy policy reaches 27% of what real answers earn, and matches on 1.8% of questions — the empty-answer slice, exactly as predicted. The reward is not trivially exploitable, and that is now a measured number rather than a hope. This probe is also what caught the scale_rewards default above.

06 Reasoning traces by rejection sampling

The original training data instructed the model to think before answering, but the "thinking" was one hardcoded sentence repeated across all 5,378 examples. As scratch paper that is blank — it carries no information about the specific question, so the model learns to recite a preamble.

The replacement is rejection sampling (STaR): have a larger model solve each training question eight times showing its work, then execute every attempt and keep only traces whose SQL is correct. The execution filter is the entire technique — a large model is wrong confidently and fluently, and training on fluent wrong reasoning is worse than not training. Yield: 4,823 verified traces, 90.8% question coverage, median 114 words of reasoning naming real tables and columns.

And it made the model worse44.6% → 41.8%. The cause was arithmetic, not conceptual.

The SQL barely changed size; 114 words of prose grew around it. At identical epochs and learning rate, the model was getting 3.4× less training on the part that gets scored. Paying for it with more epochs recovers and exceeds: 41.8% → 47.1%.

But the gains did not stack. RL on top of the trace model was a wash — +0.1 points, 179 fixed against 177 broken. Both interventions attack schema hallucination, and RL is better at it, so the traces did a partial version of RL's job and left it nothing to do.

07 Technique versus scale

The obvious challenge to any result like this is "you just needed a bigger model". That is an empirical question, so: run the old recipe and the new recipe on the same larger, code-pretrained base.

Both matter and they saturate against each other. Technique is worth +20.9 points even on a 3× larger code-pretrained base, so the pipeline is not merely compensating for a weak model. But that is half its value at 0.5B, and the effects do not add: 4.6% to 67.9% is +63.3 total against +82 if they were independent.

The ablation was built deliberately generous to the old recipe — its destructive pre-training stage omitted, its vocabulary-corrupting library omitted, the working stop token used. It is the strongest fair version of the thing it loses to.

Negative result worth reportingRL's contribution collapsed as the base improved: +5.1 at 0.5B, +0.2 and not significant at 1.5B. Every diagnostic still improved — hallucinated columns down 23%, execution rate 88.2% → 90.6%, syntax errors 5 → 2. Everything improved except the score. The reward pays for executability, and at 1.5B executability had stopped being the bottleneck. Also: 56% of training groups produced no gradient because the model now agrees with itself. RL gets harder as the policy gets better, because it runs on within-group disagreement.

08 Inference-time: retry on rejection

At 68.1%, the remaining failures split into two populations that need completely different treatments:

1,462  correct                                        68.1%
  483  runs perfectly, answers the wrong question     22.5%   no error exists
  202  the database rejects it                         9.4%   an error message exists

The second group has a signal to work with. Feed the database's error back and let the model try again, up to three rounds. Two details make it a measurement rather than a demo:

The loop never sees the reference answer. Its only stopping signal is the executor's status, which is all that exists at inference time. A loop that consulted gold would be measuring something that cannot exist in production.

Rounds are batched, not per-example. Round 1 generates all 2,147; only the ~200 rejections enter round 2. Per-example looping is roughly 50× slower for an identical answer.

Why it underperforms

202  rejected on attempt 1
 63  became executable      31% of rejections
 23  were actually correct  37% of repairs
 40  moved from "database refused it" to "runs fine, wrong rows"

There are two multiplications here, not one. An error message tells you that you are wrong, never what is right — so the model fixes the complaint rather than the answer, and two-thirds of repairs migrate from the visible failure bucket to the invisible one.

At 0.5B the loop does essentially nothing: 500 rejections, 12 repaired. A weak model told "no such column: X" still cannot determine which column does exist.

Note on statisticsMcNemar's test is not reported for retry, deliberately. Retry cannot break anything by construction — an errored attempt can never match the reference, so replacing it only ever helps. broke = 0 in all four runs (verified, not assumed) and any positive count is trivially "significant". The honest frame is effect size against cost.

09 Inference-time: execution voting

The 483 queries that run cleanly and answer the wrong question produce no error, so retry is structurally blind to them. But they disagree with their siblings, and disagreement is a signal.

Sample k candidates, execute all of them, group them by the rows they return rather than by the SQL text, and answer with the largest group. Two queries written completely differently that return identical result sets are probably both right; a hallucinated one usually returns something nobody else got.

Grouping uses the comparison function, not a hash

clusters = []
for i, candidate in enumerate(candidates):
    if candidate.status != "ok":       # a rejected query has no answer to agree with
        continue
    for indices in clusters:
        rep = candidates[indices[0]]
        if compare(candidate.rows, rep.rows, requires_order(rep.sql)):
            indices.append(i); break
    else:
        clusters.append([i])
clusters.sort(key=lambda ix: (-len(ix), min(ix)))   # deterministic

Hashing the result set would be faster and wrong. compare runs a bounded column-permutation search, so SELECT age, name and SELECT name, age are one answer — a hash splits exactly the groups voting exists to merge. At k=8 that is 28 comparisons per question at ~0.04 ms each.

Two properties are enforced rather than hoped for. candidates[0] is always the greedy sample, so vote@1 reproduces the plain greedy score exactly — a wiring-bug detector — and ties break toward it. And because a vote at budget k only needs the first k candidates, one generation run yields the entire k-curve at no extra cost.

The empty-result trap

Empty result sets all compare equal to each other regardless of why they are empty. A broken filter, a hallucinated condition matching nothing, and a genuinely empty answer land in one cluster and vote as a bloc. Unlike every other cluster, where agreement is evidence of correctness, an empty cluster's size mostly measures how many ways there are to return nothing. Three people shrugging is not a consensus.

Empty clusters are therefore demoted below any non-empty cluster. Both sides of that trade are measured: it is worth +1.3 points, and it costs 6 questions where the reference answer really was empty.

But pass@k keeps climbing, so the selection gap widens from 0.0 to 4.8 points. Sampling harder raises the ceiling faster than majority voting can reach it. At k=16 the bottleneck is no longer generating a right answer; it is recognising the one already in hand. Measured at k=8 alone this looks like a technique with room left in it, and it is not.

McNemar is legitimate here, because voting can and did break things — 8 regressions makes the test two-directional again.

Two results worth separating. Voting reaches the bucket retry cannot (38 fixes). And it also beat retry on retry's own ground: 45 rejected queries repaired against retry's 23. Seven more samples is a better repair mechanism than one error message.

The generalisable claimAcross both model sizes: retry buys +1.1 / +0.2, voting buys +3.5 / +3.0. Retry needs a model good enough to act on feedback; voting only needs one that is right sometimes, then fishes that answer out. The second is a far weaker requirement, which is why voting survives at a scale where retry collapses.

A bucket that only exists at k=1691 questions (4.2%) where not one of sixteen samples produced a runnable query. Accuracy there is 0.0% by construction. At k=8 these are diluted into the low-agreement band; at 16 they separate cleanly, and the service can identify them before answering. Declining to answer 4.2% of questions is cheaper than being wrong on them.

When the model agrees with itself it is right 85% of the time, and that covers 70% of questions. When it does not, it is close to a coin flip. In a product that is the difference between silently returning a wrong number and saying "I am not confident about this one".

Three things make it honest. Each bucket reports the pooled accuracy of its own members — an earlier version bundled 7-of-8 (62.8%) with 6-of-8 (47.9%) and reported 62.8%, overstating the weaker half by 15 points. The buckets are coarse because below 7-of-8 the raw curve is noise on samples of 27–110: 2-of-8 scores above 4-of-8. And a single greedy sample reports unmeasured with no number rather than inventing one — a service reporting a confidence it has not calibrated is worse than one reporting none.

The pattern replicates at 0.5B, shifted down (80.7% unanimous), which makes it a property of the method rather than a quirk of one checkpoint.

The remaining gap is selection, and heuristics cannot close it

Voting picks a wrong answer while holding a correct one 3.6% of the time — larger than everything retry bought, and reachable with no training and no GPU. Before building a smarter selector we characterised the failures: 87% are cases where the wrong answer won six votes to two. No frequency-based rule can override that. Two smarter selectors were built and measured at +0.1 and −0.1. Closing that gap needs a learned verifier, not a tiebreak rule.

11 Schema retrieval

Every number so far hands the model the complete, correct schema for the exact database. Real databases have hundreds of tables and do not fit in a context window. This section replaces that gift with a search problem.

Building a benchmark that can measure anything

Spider's databases have a median of 4 tables and 19 columns, rendering to ~102 prompt tokens. Retrieval over that measures nothing. The obvious fix — pool all 206 databases into one haystack — fails for a reason worth recording:

125 table names appear in more than one database
436 of 1,053 tables affected  (41%)

customers  → 22 databases      student → 12
addresses  → 15                staff   → 11

A question about "customers" is then genuinely ambiguous, and no retriever can resolve it, because the question does not disambiguate. Such a benchmark would measure an impossible task and attribute the failure to the retriever.

The pool is instead a collision-free subset: databases taken in descending order of how many benchmark questions they carry, skipping any whose table names clash with one already taken. Result: 81 databases, 300 tables, 1,427 columns, 1,457 of 2,147 questions, zero duplicate names. 107 of those tables belong to databases that carry questions; the other 193 are pure distractors. It renders to 8,262 tokens against a 3,072-token input limit, so retrieval is mandatory rather than decorative.

Two retrievers

Each table becomes one document, "student: id, name, age, dept_id". The query is the question text and nothing else — never the database id, which would leak the answer.

BM25, keyword scoring, implemented directly. The tokeniser splits snake_case and camelCase while keeping the joined form, so city_code yields ["city_code", "city", "code"]. Without that, a question saying "city" cannot match a column named city_code — which is most of what schema linking is.

Dense, a sentence embedding model with mean pooling over the attention mask and L2 normalisation, scored by dot product.

Retrieval is a noise problem at least as much as a search problem.

Turning the dial: k = 5, 10, 20

Why the aggregate says nothing hereDense reads 44.3 → 45.2 → 44.8 across a fourfold change in k. Flat — and flat because two opposing effects cancel, not because nothing happens. Coverage climbs 79% → 90% while accuracy on covered questions falls 56% → 49%. bm25 starts so recall-starved (54% coverage at k=5) that the coverage gain dominates and its aggregate climbs 35.3 → 39.0, while its covered-accuracy falls on exactly the same schedule, 64% → 57% → 54%. Whether enlarging k appears to help depends only on whether the retriever still had recall to gain — never on distraction going away, which worsens in every condition tested.

So the practical reading is narrower than "retrieve less". The retrieved set size is not a dial worth tuning: it trades coverage against distraction at roughly one-for-one, and the 16.5-point distraction penalty survives every setting. What would actually move this is making the model robust to irrelevant tables — training on cluttered schemas rather than clean ones — which is a training change, not a retrieval change.

12 Serving and latency

The service reuses the voting and retry modules directly rather than reimplementing them. That is the point: a second copy of the clustering or selection logic could drift from the numbers those techniques were measured at, and nothing would say so. A request returns the SQL, the rows, a calibrated confidence, and a timing breakdown.

Measured on one A10G handling one request at a time — which is what a service does, unlike the evaluation harness that batches sixteen. Over the full split, so the accuracy column is evidence rather than a sanity check: 6,650 seconds for the greedy pass, 14,022 for voting, 8,600 for retry, about eleven GPU-hours in total.

Where each technique keeps its costRetry's median is indistinguishable from greedy — 2,714 ms against 2,652 — because most requests never enter the loop. All of its cost sits in the tail, and its mean of 3,777 ms hides that from both directions at once: 40% above a median that reflects most requests, and 76% below a p99 that reflects the ones a user complains about. Voting is the opposite shape: 2.1× more expensive at the median and only 2.7× its own median at p99, so what you measure in staging is what you get in production.

And the earlier version of this section was wrongMeasured over 100 questions, retry's p99 read 28,140 ms and this section claimed the tail "inverts the ranking" — retry catastrophic where voting was merely expensive. Over 2,147 it is 16,042 ms, and at p95 retry is cheaper than voting (9,739 against 10,789). A p99 over 100 samples is the single slowest request in the sample, which makes it an anecdote with a statistic's name. The direction of the original finding survives — retry concentrates its cost in the tail and the mean conceals it — but the 3.3× figure was one unlucky request, and the ranking it implied does not hold.

14 Anatomy of the remaining 32%

A single accuracy number says how often the system is wrong and nothing about how. classify_error already buckets the queries that fail to run — schema hallucination, syntax, timeouts — but at grpo-coder15 the execution rate is 90.6% against 68.1% accuracy, so roughly 22 points of the split produce a perfectly valid query that returns the wrong rows, and that was one undifferentiated bucket. Splitting it means asking how the returned table differs from the reference one, relaxing a single rule at a time.

Two things this changesSchema hallucination is still the largest single failure at 8.1% — larger than any wrong-answer category, after RL already cut it 29%. The model invents a column name more often than it gets the logic wrong, which points the next round of work at the schema representation rather than at reasoning.

And set_vs_multiset puts a number on a caveat that was previously a hedge. Those 35 questions are correct as sets and differ only in duplicate rows — exactly the population Spider's official evaluator counts as right and this project's stricter multiset comparison counts as wrong. Under the official semantics this system scores 69.7%, not 68.1%. The stricter metric was the right choice, and it costs a measurable 1.6 points rather than an unknown amount.

order_only at 4 questions is worth recording as a non-problem: ORDER BY handling is effectively solved here, and any effort aimed at it would buy at most 0.2 points.

15 What we got wrong

The project began by measuring its own pipeline at 6.4% against an untrained baseline of 17.4%. Nearly every defect since has shared one shape: it produced a plausible number rather than an error. A representative selection, with the wrong version kept beside the corrected one.

A library rewrote the tokenizer vocabulary

WrongUnsloth's get_chat_template swapped the ids of two special tokens during training, so every checkpoint carried a corrupted vocabulary.

CorrectedPaired with a standard tokenizer, generation never stops and every score reads near zero for reasons unrelated to the model. Dependency removed entirely; a startup assertion now makes it unreproducible.

You cannot teach a base model a token it never learned

WrongTraining told the model to end its turn with <|im_end|>. The data was right, loss covered the token, two epochs ran — and the model emits it essentially never.

CorrectedThe base carries that token untrained: its embedding sits at the 1.5th percentile of row norms against the 98.4th for the token it does use. LoRA does not train embeddings, and this model ties the embedding to the output head, so the gradient had nowhere to go. A five-second check now runs before adopting any new base.

An assertion that passed on the broken checkpoint

WrongThe existing stop-token guard compared the tokenizer's configuration to the saved tokenizer's configuration.

CorrectedThey agreed with each other, and the weights agreed with neither. Two configurations agreeing tells you nothing about what the weights do. The replacement generates text and inspects it.

Three checkpoints never stopped generating — for three phases

WrongNot one of 2,147 generations from three models terminated cleanly; each ran to the token cap filling the tail with memorised text.

CorrectedInvisible because the output parser cut at the closing tag and cleaned up every time. Accuracy was unaffected; the cost was 6–8× the compute per evaluation — a 0.5B model took 2,139 s where a larger one took 793 s. Now a column in every results table.

Prompt truncation deleted the question

WrongOver-length prompts truncate in whichever direction the tokenizer prefers; the default is from the right, which keeps the schema and removes the question.

CorrectedThe reward would then penalise the model for not answering a question it was never shown. Direction set explicitly, plus a pre-flight assertion that nothing truncates at all.

A dependency that was never declared

WrongRemoving the obsolete training library broke three test modules: peft, which applies the adapters, was only ever installed because that library depended on it.

CorrectedIt is imported directly, on the critical path of every number in the project — so a fresh clone had been broken the whole time. An import audit now backs the dependency list.

Two predictions, both wrong, both instructive

WrongPredicted +4 points from the retry loop; predicted 58–61% under retrieval.

CorrectedGot +1.1 and 45.2%. The first assumed a repaired query is a correct query; the second assumed accuracy scales with retrieval coverage. Both errors located a specific missing term in the model of the system — which is what stating a prediction beforehand buys you.

16 Limitations and next steps

Multiset comparison reads lower than published Spider numbers, which use set semantics. Comparisons against the literature need that adjustment.

The retrieval benchmark is constructed. A collision-free pool of 300 tables is a defensible stand-in for a warehouse, but it is not one, and it covers 68% of the test split rather than all of it.

The confidence calibration is from a single measurement — one checkpoint, one k, one benchmark. It should be recalibrated per deployment rather than trusted as a constant.

Retry and voting are not composed. Retrying each sampled candidate and then voting is the natural combination and is not implemented; the batched retry design does not distinguish the greedy candidate from a sampled one, which voting's ordering depends on.

What the measurements point at next, in order of expected value:

Prune the retrieved set rather than enlarge it. Distraction is the dominant retrieval cost, so a smaller k or a second-stage filter before the prompt. The oracle condition proves 68.4% is available if the schema arrives clean.

A learned verifier for the 3.6% where a correct candidate is generated and not selected. Heuristics are measured dead on arrival there.

Continuous batching for the 2.8-second median, which is the single biggest serving weakness.

Not trajectory-level RL, the original plan. The ceiling is not repair rate but that only 37% of repairs are correct, and 56% of training groups already produce no gradient at 1.5B — trajectory training makes that worse.
